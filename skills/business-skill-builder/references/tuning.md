# Skill 效果不好时的调整流程

核心原则：先找出问题在哪，再动手改。效果不好大多是业务方法没写清楚，很少是提示词问题。

## 1. 拿真实案例对比
请用户提供：skill 的输出 + 他自己做的结果（或当时的实际做法）。只说“效果不好”时，先要这两样东西。找出**第一个不一样的地方**。

## 2. 对照诊断

| 现象 | 问题通常出在哪 | 怎么改 |
|---|---|---|
| 没用这个 skill，或用错 skill | “什么时候用”不清楚 | 补适用 / 不适用场景，加入同事的原话 |
| 步骤漏了或顺序乱 | 步骤太粗 | 拆细漏掉的那一步，写明先后依赖 |
| 步骤对、判断错（最常见） | 判断规则缺失或模糊 | 写成“如果……就……”，补阈值和例外 |
| 结论对、写得不像 | 缺好结果样例 | 补真实好案例和输出格式 |
| 编数据或替人做决定 | 缺“缺数据怎么办”“谁说了算” | 写明先问不要猜、哪些必须人确认 |
| 只有某类情况错 | 漏特殊情况 | 单独加一条规则 + 一个反例 |
| 输入数据本身缺 / 错 | 数据问题 | 先修数据，不改规则 |

## 3. 追问原因
可以在用户的会话里让 skill 说明：“为什么得出这个结论？用了哪条规则？”
- 没找到相关规则 → 方法文档缺规则
- 理解成别的意思 → 规则有歧义，改写
- 规则冲突 → 补优先级

## 4. 改方法文档，再重新生成
1. 只给出方法文档要改的那几段，请用户确认（**一次只改一处**）。
2. 能合并成通用规则的就合并，不要每错一次加一条。
3. 根据方法文档重新生成 skill，在变更记录加一行：日期、改了什么、因为哪个案例。

## 5. 重跑所有验收样本
- 新旧样本全部重跑，防止修一个坏一个。
- 这次做错的案例加入验收样本。

## 何时停止调
改了 2～3 轮仍不稳定，且这件事主要靠经验和感觉：建议把它写进“谁说了算”，让 AI 只给参考信息，由人决定。两个人做法不同导致的摇摆，先请他们对齐。
