# 生成 skill 的格式要求

这部分是 AI 负责的“规范”，不需要业务同学理解。

## 文件结构

```text
<skill-name>/
├── SKILL.md            必需：说明 + 正文
└── references/         可选：内容多时才拆
    ├── cases.md        好案例、反例（已脱敏）
    └── <其他资料>.md    话术库、品类规则表、模板等
```

内容少时全部放在 SKILL.md 里即可，不要为了“规范”硬拆文件。验收样本和变更记录留在方法文档里，不放进 skill。

## SKILL.md 写法

```markdown
---
name: <小写英文和连字符，如 review-planning>
description: <做什么 + 什么时候用，包含用户常说的原话；必要时写一句不适用场景>
---

# <中文名称>

## 适用 / 不适用
## 需要的输入（缺了怎么办）
## 步骤
## 判断规则（如果……就……；冲突优先级）
## 输出格式
## 必须由人确认的事项
## 参考资料（需要时再读 references/ 下哪个文件）
```

## 质量要求

- **description 决定 AI 会不会调用它**：写清楚做什么、什么时候用，放进同事的真实说法；不要写成能力大全。
- **只写改变 AI 决策的内容**：业务判断、阈值、例外、口径。删掉“要认真”“要专业”之类的空话。
- **判断规则保持用户原意**：可以改写得更清楚，不能改变含义、不能补充用户没说的数字。
- **缺数据时**：写明“先问用户”还是“标注缺失后继续”，禁止 AI 自行估算编造。
- **人工确认点**写成明确指令：“输出建议后停止，等待用户确认”。
- 待补项不能留在 skill 里；还没补的，要么回去追问，要么写成“由人判断”。

## 交付前自查
- [ ] 方法文档里每条判断规则在 skill 中都有对应
- [ ] 没有用户未提供的数字或规则（示例值已明确标注）
- [ ] 案例已脱敏
- [ ] 已用验收样本试跑并请用户确认
